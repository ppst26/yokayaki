# Specification: Hybrid Ordering System (order.md)

เอกสารอธิบายการทำงานและตรรกะเบื้องหลังระบบสั่งอาหารไฮบริด (Hybrid Ordering) ของร้าน Yokayaki Izakaya ซึ่งแบ่งออกเป็น 2 ช่องทางหลัก: พนักงานสั่งผ่านเครื่อง POS และลูกค้าสแกน QR สั่งผ่านมือถือส่วนตัว

---

## 1. ภาพรวมการไหลของข้อมูลออเดอร์ (Order Data Flow)

ระบบสั่งอาหารจะทำงานสัมพันธ์กันบนฐานข้อมูล Supabase และการอัปเดตสถานะแบบเรียลไทม์:

```
[ช่องทาง 1: พนักงานคีย์สั่งบน POS] ────┐
                                   ├──> [RPC ตรวจสต็อก & สร้าง/อัปเดต Order] ──> [อัปเดตสถานะโต๊ะ occupied]
[ช่องทาง 2: ลูกค้าสแกน QR สั่งบนมือถือ] ┘
```

---

## 2. สถานะของออเดอร์และรายการอาหาร (Order & Item States)

สถานะในระบบจะถูกแบ่งออกเป็น 2 ระดับเพื่อการควบคุมที่ละเอียด:

### 2.1 สถานะของบิล (Order Status)
เก็บค่าไว้ในฟิลด์ `orders.status` มี 3 สถานะ:
- **`active`**: บิลยังเปิดอยู่ ลูกค้ากำลังรับประทานอาหาร สามารถสั่งอาหารเพิ่มได้เรื่อยๆ
- **`completed`**: บิลชำระเงินเรียบร้อยแล้ว ถูกปิดเรียบร้อย โต๊ะจะว่างพร้อมรับลูกค้าใหม่
- **`voided`**: บิลถูกยกเลิกทั้งหมด (ใช้เมื่อกรณีลูกค้าลุกโดยไม่กิน หรือเกิดข้อผิดพลาดรุนแรง)

### 2.2 สถานะของแต่ละรายการอาหาร (Order Item Status)
เก็บค่าไว้ในฟิลด์ `order_items.status` มี 3 สถานะ:
- **`pending`**: รายการอาหารเพิ่งสั่งเข้ามา กำลังรอคิวทำ/กำลังทำในครัว
- **`served`**: พนักงานเสิร์ฟอาหารจานนี้สำเร็จแล้ว (เมื่อกดรับเงินชำระบิล รายการ pending ทั้งหมดจะถูกเปลี่ยนเป็น served อัตโนมัติ)
- **`voided`**: รายการอาหารถูกยกเลิกโดยพนักงานบริการ (ระบุสาเหตุ และบันทึกประวัติลง `void_logs`)

## 3. ตรรกะเบื้องหลังการสั่งออเดอร์ (Database RPC Stored Procedures)

เพื่อป้องกันการแย่งสั่งออเดอร์จนสต็อกติดลบ (Race Conditions) ระบบ Yokayaki จึงไม่ใช้วิธีสั่งซื้อผ่าน API ปกติ แต่ใช้การรันฟังก์ชันในตัวฐานข้อมูลโดยตรง (Database RPC)

### 3.1 การสั่งซื้อฝั่งพนักงาน (`place_order_item`)
พนักงานจะสั่งอาหารโดยใช้ฟังก์ชัน `place_order_item(p_table_id, p_menu_item_id, p_quantity, p_unit_price)`:
1. ทำการล็อกแถวข้อมูลเมนูที่ต้องการสั่งเพื่อเช็คจำนวนสต็อกล่าสุด (`FOR UPDATE`)
2. หากสต็อกเพียงพอ:
   - ตรวจหาบิลสถานะ `active` ของโต๊ะนั้นๆ หากยังไม่มีจะสร้างบิลใหม่ขึ้นมาทันที และปรับสถานะโต๊ะเป็น `occupied`
   - ทำการเพิ่มรายการลงในตาราง `order_items`
   - ทำการหักลบจำนวนสต็อกในตาราง `menu_items` ทันทีแบบ Atomic
3. หากสต็อกไม่พอ จะส่งค่า `false` กลับไปแจ้งข้อผิดพลาดบนหน้าจอ POS ทันที

### 3.2 การสั่งซื้อฝั่งลูกค้า (`customer_place_order_item`)
ลูกค้าสแกน QR จะใช้ฟังก์ชัน `customer_place_order_item(p_session_id, p_menu_item_id, p_quantity, p_unit_price)`:
1. ตรวจสอบความถูกต้องของ `session_id` (UUID) ว่ายังมีสถานะเป็น `active` และยังไม่หมดเวลา (`expired_at < NOW()`)
2. หากเซสชันปกติ จะดึง `table_id` ที่ผูกกับเซสชันนั้นออกมา
3. ดำเนินการเช็คสต็อก หักสต็อก และใส่รายการในตาราง `order_items` เช่นเดียวกับการสั่งของพนักงาน

## 4. ลอจิกการล็อกราคาและโปรโมชัน (Order-Time Price Lock)

เนื่องจากร้านมีระบบลดราคาช่วงเวลาพิเศษ (Happy Hour) ราคาสินค้าจึงอาจปรับเปลี่ยนตามช่วงเวลาจริง:
- **หลักการล็อกราคา:** เมื่อออเดอร์ถูกยิงเข้าระบบ ราคาจานนั้นๆ จะถูกบันทึกเด็ดขาดลงฟิลด์ `unit_price` ในตาราง `order_items` ทันที
- **ผลลัพธ์:** แม้ว่าเวลาจะเลยพ้นช่วง Happy Hour ไปในขณะที่ลูกค้าเรียกคิดเงิน บิลก็จะยังคงคำนวณราคาตามยอด `unit_price` ในตอนสั่ง ไม่ปรับขึ้นเป็นราคาปกติ ป้องกันข้อโต้แย้งเรื่องราคากับลูกค้าได้อย่างสมบูรณ์

---

## 5. ตรรกะการยกเลิกรายการอาหาร (Void Flow & Stock Logic)

เมื่อต้องการยกเลิกอาหาร พนักงาน (Staff/Owner) จะระบุตัวตนและกดปุ่ม Void ผ่านหน้า POS:
1. พนักงานต้องระบุสาเหตุ: **"คีย์ผิดพลาด"** หรือ **"อาหารชำรุด"**
2. ระบบจะบันทึกประวัติลงตาราง `void_logs`
3. **ผลกระทบต่อสต็อกสินค้า:**
   - **กรณี คีย์ผิดพลาด:** ระบบจะบวกจำนวนสต็อกกลับคืนตาราง `menu_items` อัตโนมัติ เพราะไม่มีการสูญเสียวัตถุดิบจริง
   - **กรณี อาหารชำรุด:** ระบบจะเปลี่ยนสถานะรายการอาหารเป็น `voided` แต่ **ไม่บวกสต็อกคืน** เนื่องจากวัตถุดิบเสียหายไปแล้วจริง โดยจะบันทึกเป็นยอดขยะสูญเสียเพื่อใช้ตรวจสอบสิ้นเดือน
