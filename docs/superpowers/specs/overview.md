# Project Overview: Yokayaki Izakaya POS

เอกสารภาพรวมระบบระบบ POS ร้านอาหารสไตล์อิซากายะขนาดเล็ก (3-4 โต๊ะ) โฟกัสการทำงานที่รวดเร็ว ลื่นไหล ป้องกันเงินรั่วไหล และมีความคล่องตัวสูง

---

## 1. คอนเซ็ปต์หลัก (Core Concept)

ระบบ POS ที่ทำงานแบบ **"ไฮบริด (Hybrid)"** ได้รับการออกแบบมาเพื่อแก้ปัญหาร้านอิซากายะแนวแฮงเอาต์ ซึ่งลูกค้ามักจะสั่งอาหารและเครื่องดื่มแบบ "ทีละนิดแต่สั่งเรื่อยๆ" ตลอดทั้งคืน ระบบจึงรองรับการรับออเดอร์สองช่องทางพร้อมกันอย่างไร้รอยต่อ:

### 1.1 การรับออเดอร์แบบไฮบริด (Two-Way Ordering)
1.  **Staff Terminal (พนักงานหน้าร้านสั่ง):** พนักงานคีย์อาหารผ่านเครื่อง POS หลักของร้าน (เช่น แท็บเล็ตส่วนกลางของร้าน) สำหรับลูกค้าที่ต้องการการบริการแบบดั้งเดิม หรือสั่งอาหารสดที่หน้าร้าน
2.  **QR Order (ลูกค้าสั่งเองผ่านมือถือ):** ลูกค้าสแกน QR Code ประจำโต๊ะที่พิมพ์ใหม่ทุกครั้งเพื่อดูเมนู และส่งออเดอร์ตรงจากโทรศัพท์มือถือของตัวเอง โดยไม่ต้องคอยเรียกหาพนักงาน

### 💡 ตัวอย่างสถานการณ์จำลอง (Use Case Scenario)
*   **สถานการณ์สั่งเพิ่มรัวๆ:** ลูกค้าโต๊ะ 3 นั่งสแกนสั่งเบียร์สด 2 แก้วผ่านระบบ QR Order ยอดคำสั่งซื้อจะเด้งตรงเข้าหน้าจอครัวทันที พนักงานไม่ต้องเดินมารับออเดอร์
*   **สถานการณ์สั่งหน้างาน:** ระหว่างเดินไปเสิร์ฟเบียร์ที่โต๊ะ 3 ลูกค้าขอสั่ง "แก้มปลาต้มซีอิ๊ว" เพิ่มเติมแบบปากเปล่า พนักงานสามารถเดินไปที่เครื่อง POS หน้าร้าน กดเลือกโต๊ะ 3 แล้วคีย์ออเดอร์ส่งเข้าครัวได้ทันที
*   **การซิงค์ข้อมูล (Real-time Sync):** ทั้งยอดคำสั่งซื้อของพนักงานและลูกค้าจะมาเชื่อมเข้าที่บิลโต๊ะ 3 เดียวกันบนฐานข้อมูล Supabase ทันที ทำให้ลูกค้าดูบิลบนมือถือตนเองเห็นราคาอัปเดตเรียลไทม์ และพนักงานแคชเชียร์เห็นยอดตรงกัน 100%

## 2. ขอบเขตของร้านค้าและเป้าหมาย (Scope & Target)

ระบบนี้ปรับแต่งมาเพื่อความกระชับ รวดเร็ว และประหยัดค่าอุปกรณ์ เหมาะกับร้านอาหารสเกลเล็กที่ดูแลได้ทั่วถึง

### 2.1 ขอบเขตร้านค้าและขนาดพื้นที่ (3-4 Tables Scope)
*   **ความกระชับของหน้าจอ:** หน้าจอผังโต๊ะ (Table Map) จะถูกออกแบบมาให้มองเห็นสถานะของทั้ง 4 โต๊ะได้ครบถ้วนในหน้าแรกทันทีโดยไม่ต้องเลื่อนหน้าจอ (Scroll)
*   **การบริการที่รวดเร็ว:** เนื่องจากมีเพียง 3-4 โต๊ะ ครัวและพนักงานจะอยู่ใกล้กันมาก ระบบจึงส่งออเดอร์ตรงเข้าครัวทันที (Direct Fire) เพื่อลดทอนปุ่มกดยืนยันออเดอร์ลง ทำให้การเสิร์ฟรวดเร็วที่สุด

### 2.2 ผู้ใช้งานหลักและสิทธิ์การเข้าถึง (Primary Users & Permissions)
ระบบแบ่งบทบาทหน้าที่อย่างเด็ดขาดเพื่อป้องกันช่องโหว่เงินรั่วไหล:

#### 👑 OWNER (เจ้าของร้าน / ผู้จัดการ)
*   **บทบาท:** มีอำนาจสูงสุดในร้าน ตรวจสอบรายงานบัญชี และตั้งค่าการขาย
*   **สิทธิ์การใช้งาน:**
    *   ดูหน้า Dashboard สรุปยอดขายรวมและสถิติยอดขายรายชั่วโมง
    *   ดึงรายงานการปิดยอดสิ้นวัน (EOD Reports)
    *   แก้ไข เพิ่ม/ลด รายชื่อเมนู ปรับราคาขาย และเปิด/ปิดโปรโมชัน Happy Hour
    *   เข้าตรวจสอบตารางประวัติการยกเลิกอาหาร (Void Logs) ทั้งหมดของร้าน
*   **ตัวอย่าง:** พี่พี (Owner) นั่งอยู่ที่บ้าน สามารถเปิดแอปมือถือ ล็อกอินด้วย PIN 6 หลักของตนเองเพื่อตรวจสอบยอดขายวันนี้ และตรวจสอบว่าทำไมวันนี้พนักงานหน้าร้านกดยกเลิกเมนูเบียร์ไป 3 แก้ว พร้อมตรวจสอบเหตุผลย้อนหลังได้ทันที

#### 💁‍♂️ STAFF (พนักงานหน้าร้าน)
*   **บทบาท:** ดูแลการบริการ รับออเดอร์ เสิร์ฟอาหาร และเก็บเงิน
*   **สิทธิ์การใช้งาน:**
    *   ใช้งานได้เฉพาะหน้าผังโต๊ะ (Table Map) และหน้าคีย์สั่งอาหาร/เช็คบิล (POS Screen)
    *   **การยกเลิกออเดอร์ (Void):** สามารถกดยกเลิกรายการอาหารได้เองเพื่อความรวดเร็ว แต่ระบบจะบังคับให้เลือกสาเหตุที่ยกเลิก และจะบันทึกเหตุผลพร้อมยอดเงินลง Void Logs อัตโนมัติเพื่อให้ Owner ตรวจสอบย้อนหลังได้
    *   *ข้อจำกัด:* ไม่มีสิทธิ์ดูหน้ายอดขายรวมของร้าน และไม่สามารถเข้าไปตั้งค่าหรือเปลี่ยนราคาสินค้าใดๆ ได้
*   **ตัวอย่าง:** น้องพนักงานหน้าร้านจะเห็นหน้าจอ POS เฉพาะปุ่มเปิดโต๊ะ คีย์อาหาร และปุ่มชำระเงินเท่านั้น โดยไม่มีเมนู "รายงานยอดขาย" หรือ "ตั้งค่าราคาเมนู" แสดงบนหน้าจอของตนเอง

### 2.3 ระบบรักษาความปลอดภัยระดับร้านค้า (Security PIN & Theft Prevention)
*   **PIN Code 6 หลัก:** พนักงานแต่ละคนจะได้รับรหัส PIN 6 หลักเฉพาะตัว (การใช้ 6 หลักป้องกันการแอบมองรหัสและการสุ่มเดาได้ดีกว่า 4 หลักแบบเดิมถึง 100 เท่า)
*   **การล็อกระบบอัตโนมัติ (Auto-Lock):** หากเครื่อง POS หลักไม่มีการขยับหรือเคลื่อนไหวเป็นเวลา 5 นาที หน้าจอจะล็อกตัวเองกลับไปหน้าให้ป้อนรหัส PIN ทันที ป้องกันพนักงานแอบใช้เครื่องในสิทธิ์ของผู้อื่น
*   **ระบบตรวจสอบบัญชี (Audit Trail):** ทุกธุรกรรมการชำระเงินสด, เงินโอน, รวมถึงการลดราคาสมาชิก และการกดยกเลิกรายการอาหาร (Void) จะถูกบันทึกชื่อพนักงานผู้กด เวลา และเหตุผลเข้าสู่ฐานข้อมูลทุกครั้ง ไม่สามารถลบประวัติตรงนี้ได้

## 3. โครงสร้างเทคโนโลยี (Tech Stack)
* **Frontend:** Next.js (App Router, Tailwind CSS, shadcn/ui)
* **Backend:** Next.js Server Actions / API Routes
* **Database & Real-time:** Supabase (PostgreSQL, Supabase Realtime สำหรับส่งข้อมูลออเดอร์เข้าครัว และ Row Level Security - RLS)
* **Deployment:** Vercel (หรือตามต้องการ)

---

## 4. แผนผังฐานข้อมูลเบื้องต้น (Database Schema Overview)
ความสัมพันธ์ของข้อมูลจะถูกเชื่อมต่อกันผ่านตารางหลักๆ ดังนี้:
* `employees` ➡️ จัดเก็บสิทธิ์และรหัส PIN 6 หลัก
* `tables` ➡️ จัดเก็บผังโต๊ะและสถานะความว่าง
* `qr_sessions` ➡️ ควบคุมเซสชันสั่งอาหารแบบไดนามิกของลูกค้า
* `menu_items` ➡️ จัดเก็บข้อมูลราคาและสต็อกสินค้าของร้าน
* `orders` & `order_items` ➡️ ข้อมูลออเดอร์ประวัติการสั่งอาหาร
* `void_logs` ➡️ บันทึกการยกเลิกรายการอาหารโดยละเอียด
* `payments` ➡️ ข้อมูลธุรกรรมบิลแต่ละใบ
